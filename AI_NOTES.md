# AI usage notes

How the coding agent (Claude Code) was used, step by step. The instruction files it
worked from are committed: `CLAUDE.md`, `.claude/skills/*/SKILL.md`,
`.claude/agents/spec-auditor.md`, `.claude/settings.json`, `docs/ai/agent-brief.md`.
Prompts that shaped the result are in `docs/ai/prompts.md`.

Legend: **accepted** = used as produced; **rewritten** = the author changed the substance;
**cut** = dropped for time, recorded in README.

| Step | What the agent produced | Accepted / rewritten | Why |
|---|---|---|---|
| 1 | `SPEC.md` v1 from the brief: contract, 43 rules, edge cases, constants table, NFR targets, matrix. | Rewritten in three rounds before the first commit: ingredient candidates are accepted by the filter's own matching rule against corpus lines (not a token vocabulary); `INGREDIENT_GROUPS` (nut, dairy, meat, fish, seafood); veto terms match whole words with `VETO_EXCEPTIONS`; stopwords `one, way, time, clue, idea`. The agent added `INGREDIENT_MIN_CHARS = 3` and flagged it. "X-free with an allergen is a safety refusal" was questioned by the agent and kept by the author. | The agent's first draft of the ingredient parser accepted any word after "with"/"without", which would have turned "dinner with friends" into a filter and refused the question. |
| 2 | `CLAUDE.md`, four skills, `spec-auditor`, hook scripts under `.claude/hooks/`, `.pre-commit-config.yaml`, `scripts/check_commit_msg.sh`, this file, `docs/ai/prompts.md`. The agent drafted `.claude/settings.json` (attribution off, permissions, hooks) but Claude Code's auto-mode classifier refused to let the agent write its own settings file; the author created it from the agent's draft. | Accepted. | Mechanical; the `attribution` value was checked against the Claude Code settings reference rather than written from memory. |
| 3 | ADR drafts 001 (retrieval unit and method), 002 (refusal and safety policy), 003 (model selection), status Proposed, numbers marked TBD with the report they will come from. | Accepted as drafts; to be revisited at steps 13–14 with measurements. | Options and "wrong when" conditions follow the brief; no prices beyond the brief's dated table. |
| 4 | uv project, contract models, `/health`, `/ask` stub, contract tests, Dockerfile (digest-pinned, non-root), Northflank template, `scripts/bootstrap.sh`, CI with deploy. | Accepted after two CI fixes: `setup-uv` has no `v10` major tag; the bootstrap script read the HTTP status inside a `$(...)` subshell and always saw 000. | Both failures were visible only in CI; the fixes are separate commits so the history shows them. First deploy succeeded at 10:43, 27 minutes after the first commit. |
| 5 | Wikitext parser (durations with fractions and ranges, labelled time parts, template parameters, sections, wikitable rows, markup cleaning, slugs, diet veto), ingest script with `--list`, manifest and revision lock, 55-recipe corpus, integrity tests. | Accepted. The agent chose the 55 pages from the `--list` table and wrote the rationale into the manifest. SPEC quota "8 pages without the template" was replaced by a measured structure quota after the agent found only two such pages in the categories used. | "Pasta recipes" and "Noodle recipes" are empty categories on Wikibooks; "Recipes using pasta and noodles" is used. Focaccia's wikitable ingredients showed up as 0 ingredients in `--list` and were added test-first. |
| 6 | Constraint parser (time → diet → ingredient markers, corpus-line acceptance, groups, stopwords) and three-valued filters; 30 phrasings plus filter tests, all written before the code. | Accepted; all 30 phrasings passed on the first implementation because the author had pinned the rules in SPEC before start. The agent added the fixed singularisation rule to SPEC when the implementation needed one. | The parser is table-driven from `config.py`; no behavior lives outside SPEC section 8. |
| 7 | Hybrid retrieval (BM25 with title boost, cosine over `text-embedding-3-small`, RRF, filters after fusion), index file with hash check, `build_index.py`, retrieval eval over 30 queries. | Accepted. The agent enlarged the fake embedder from 64 to 4096 dimensions after hash collisions made a fused-ranking test flaky, and noted that the 30-query set is too easy (1.00 in every mode) for ADR-001 to rest on it alone. | A harder query set is planned for step 13 so the mode comparison carries signal. |
| 8 | Safety gate (named patterns), `/ask` pipeline with every branch under a fake LLM, structured request log (`retrieved` plus `top_ranked`), prompt file v1, LLM interface with a per-request citation enum. | Accepted. The agent dropped the planned "Does X contain gluten?" example from SPEC E-08 because it carries no allergy wording and would have required a pattern with false positives on ordinary requests; the model's `safety` status (R-34) covers such cases. | One commit mistakenly merged the safety-gate implementation into the test commit after a hook failure left files staged; recorded here rather than rewritten. |
| 9 | Anthropic adapter with `output_config` JSON-schema output, wiring by environment, six manual questions against the real model. | Accepted after one fix: a two-recipe comparison hit the 600-token output cap and surfaced as a 503, so the cap went to 1000 in config and SPEC. Sampling parameters are not sent because current Anthropic models reject them (SPEC row `LLM_TEMPERATURE`). | The SDK usage was taken from the Claude API reference skill, not from memory; the raised cap is a SPEC change, not a hidden constant. |
| 10 | Vite + TypeScript page with four states, API types generated from the OpenAPI document (`scripts/export_openapi.py`, `openapi-typescript`), Node build stage in the Dockerfile, CI frontend job with a drift check. SPEC 3.7 was written because SPEC named the page but not its states or the type generation; the SPEC change log was filled in for v1.1–v1.7. | Accepted. The page, the Dockerfile stage and the CI job were prepared during the step-9 checkpoint and committed after it as three commits; verified in production through the browser (loading, answer, safety refusal). | The commit-message policy rejected the phrase "Claude Code" in the settings commit, so that subject says "agent settings". The safety refusal seen in the browser listed four recipes for a question about one; the author asked for a title-match rule (R-36) before step 11. |
| 10b | R-36 safety answer scope, requested by the author after seeing the browser output: the safety answer keeps the retrieved recipes whose title shares a significant word with the question (`TITLE_STOPWORDS` excluded, R-14 singularisation), all of them when none does; citations are the shown recipes; G-12 now cites the asked recipe. Three commits: SPEC, xfail tests, implementation. | Accepted as specified by the author; the agent chose the stopword list from the 55 corpus titles (articles, connectors, variant numerals). | "Is the carbonara nut-free?" listed four recipes' ingredients, three of them pesto and mac-and-cheese; the person asked about one dish. |
| 11 | Golden set (15 cases, 3 probes), harness `evals/run_evals.py` (contract validation, invariants I-05/I-07/I-08 against the corpus, assertions, JSON report with cost from `evals/prices.yaml`), prices read from the vendor pages on 2026-10-11, first local run 14/15. | Accepted after one fix: G-06 ("dessert without nuts", four retrieved desserts) ran 12.6 s into the 1000-token output cap and surfaced as a 503, so the prompt became `answer.v2` with a 150-word bound and a shape per question type; the rerun is 15/15. | A longer output cap would have hidden the problem and made latency worse; the eval case is kept as it is because recommendation questions are the ones that overflow. The local report is committed as the step-11 evidence. |
